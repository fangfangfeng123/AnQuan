本文档将以下资料合并为一份开发前设计基线：

2. `E:\xuexi\AnQuan\参考资料` 中关于多 Agent、沙箱、SAST、PoC、攻击链、CVSS 报告、AI 修复补丁的 7 份技术综述。
3. 前期梳理的端到端流程、数据对象、状态流转、变量改名点和前端模块映射。

本文档只描述实现方案，不包含程序代码。

## 1. 方案总体结论

建议采用“前端可视化工作台 + 后端任务服务 + 多 Agent 编排引擎 + 安全沙箱执行器 + 持久化数据仓库 + LLM 模型适配层”的整体架构。

核心流程固定为五阶段顺序推进：

`环境侦察 -> 源码审计 -> 动态验证 -> 攻击链推演 -> 报告生成`

主流程如下：

1. 用户输入 Git 仓库地址或本地压缩包源码。
2. 系统创建项目和评估任务。
3. 系统创建隔离沙箱，并只读挂载源码。
4. 环境侦察 Agent 识别技术栈、依赖、接口和运行方式。
5. 代码审计 Agent 执行 SAST 与污点分析，生成疑似漏洞。
6. PoC 验证 Agent 在沙箱中执行无害化动态验证。
7. 攻击链推演 Agent 将已验证漏洞组合为 DAG 攻击路径。
8. 报告模块生成结构化安全评估报告并支持导出。
9. 任务更新为已完成状态。

## 2. 总体架构

### 2.1 展示层

- 项目概览大盘：项目卡片、全局风险统计、新建评估入口。
- 安全评估工作台：流水线、终端日志、资源指标、漏洞列表、攻击链拓扑、漏洞详情。
- 安全报告中心：报告预览、风险汇总、漏洞清单、整改建议、格式导出。
- 沙箱与环境配置页：镜像、网络策略、超时、并发、模型参数、审计日志。

### 2.2 服务层

- 项目管理服务：处理项目建档、源码接入、元数据维护。
- 任务与状态服务：维护任务状态和五阶段状态。
- 多 Agent 编排引擎：调度 Recon、Code Audit、PoC Verify、Exploit Chain、Report Agent。
- 漏洞与证据服务：统一维护漏洞对象、污点路径、PoC 证据、补丁和报告数据。
- LLM 模型服务：统一封装在线 API、本地模型和演示模式。
- 扫描工具适配层：统一封装 Semgrep、CodeQL、Joern、Nuclei、ZAP 等工具结果。
- 沙箱执行服务：负责容器生命周期、命令执行、资源限制、日志回收和销毁。

### 2.3 数据层

- 关系型数据：项目、任务、漏洞、证据、补丁、报告元数据。
- 对象存储：源码快照、日志、响应报文、导出文件。
- 事件存储或消息通道：Agent 事件、实时日志、流水线状态更新。
- 配置存储：扫描规则、Source/Sink 规则、修复模式、报告模板、模型配置。

### 2.4 外部能力

- Git 仓库服务。
- 容器或虚拟机运行时。
- 大模型推理服务。
- 静态扫描、依赖扫描、动态验证工具。

## 3. 任务状态与生命周期

### 3.1 任务状态

| 状态 | 含义 | 允许进入的动作 |
|---|---|---|
| created | 已创建，待启动 | 启动评估 |
| running | 评估中 | 停止评估、等待阶段完成 |
| completed | 评估完成 | 查看报告、重新评估 |
| failed | 执行失败 | 查看错误、重新发起 |
| stopped | 用户停止 | 查看已保留的阶段性结果 |

### 3.2 阶段状态

每个阶段内部建议维护独立状态，不直接占用任务状态：

`pending -> running -> completed -> failed`

任务只有在五阶段整体运行时才处于 `running`。

### 3.3 沙箱状态

沙箱状态与任务状态分离：

`provisioning -> ready -> executing -> stopping -> destroyed`

任务停止或失败时，沙箱必须走销毁流程，但不能销毁已持久化到数据层的漏洞和证据。

### 3.4 异常与停止规则

- 用户停止任务时，立即向编排引擎发出停止信号。
- 编排引擎优先终止沙箱内正在执行的 Agent 或测试进程。
- 沙箱随后销毁，释放资源。
- 已入库的疑似漏洞、验证记录、日志和报告片段必须保留。
- 如果任务已经生成报告，则正常完成；否则保持 `stopped` 状态，不伪造报告。
- 项目删除采用归档或软删除，不应通过删除操作级联清除审计证据、PoC 证据和已交付报告。

项目自身状态只使用 `active / archived`，任务的 `created / running / completed / failed / stopped` 不得混入项目状态。

## 6. 核心业务规则

### 6.1 静态审计规则

- SAST 初筛结果只作为疑似漏洞，不直接称为真实漏洞。
- 污点分析必须区分 Source、Sink、Sanitizer。
- 只有存在未被净化或未被安全编码阻断的数据流时，才生成 Unverified 漏洞。
- 输出漏洞时同时保存文件、行号、代码片段、传播路径和风险模式。

### 6.2 PoC 验证规则

- 只有 Unverified 漏洞进入验证队列。
- PoC 只允许针对沙箱内部署的临时实例。
- PoC 不能修改真实生产数据，不能进行拒绝服务，不能创建后门。
- SQL 注入优先使用布尔差异、时间延迟或固定特征回显。
- 命令注入优先使用 echo 唯一标记，不执行破坏性命令。
- 路径遍历优先读取容器内生成的标志文件或 `/etc/hostname`，不读取真实敏感文件。
- 文件上传只能上传无害测试文件，且只在隔离环境内执行。
- 只有拿到预期特征响应，才把漏洞标记为 Verified。
- 验证失败但静态风险模式仍然成立的漏洞，统一保留为 `latent` 中低危潜在隐患，不直接删除。
- 只有验证证据能够明确证明风险模式不成立、且不存在任何残留风险时，才可标记为误报，但仍需保留审计记录。
- 前端事件中的 `poc_failed` 不应默认触发删除漏洞，应先判断转入 `latent` 还是标记误报。

### 6.3 攻击链推演规则

- 只有 Verified 漏洞进入攻击链推演。
- 单点漏洞先计算前置条件、后置能力和权限变化。
- 多个漏洞组合时，仅当上一个漏洞的后置能力满足下一个漏洞的前置条件时，才建立边。
- 攻击链必须是 DAG，避免死循环。
- DAG 允许分叉和汇合，不应把全部攻击链强制存储为单条线性路径。
- 节点顺序仅作为分层辅助；真正的依赖关系由边决定，前端按拓扑结构自动布局。
- 输出时给出从初始入口到最终目标的完整路径，并保留每个步骤对应的 findingId。

### 6.4 报告规则

- 无漏洞项目也应输出“安全”结论，而不是空报告。
- Verified 漏洞必须附完整证据。
- latent 漏洞进入风险提示，不参与攻击链。
- 修复优先级应结合漏洞严重等级、攻击可达性和业务影响。

### 6.5 数据生命周期与保留

- 项目和任务支持归档或删除，但证据、报告和审计日志的保留策略由系统配置决定。
- PoC 响应报文、已生成报告和修复记录作为交付证据保留，不应因项目软删除而永久消失。
- 任务日志、源码快照、导出临时文件可以设置保留周期，但删除前必须保留可追踪记录。
- 严重等级在数据库和 API 中统一使用 `critical / high / medium / low`。
- 综合风险等级对外展示映射为“极高危、高危、中危、低危或安全”。

## 7. 模块实现范围

### 7.1 项目接入模块

职责：

- 接收 Git 仓库地址或压缩包。
- 检查输入类型、大小和格式。
- 创建项目快照。
- 识别技术栈和依赖。
- 建立评估任务。

### 7.2 沙箱隔离模块

职责：

- 按任务创建独立沙箱。
- 只读挂载源码。
- 建立临时可写目录。
- 执行网络隔离策略。
- 执行 CPU、内存、进程、磁盘配额限制。
- 执行命令、回收日志、终止进程、销毁容器。

推荐基线：

- 运行时：Docker，高安全场景叠加 gVisor 或 Kata。
- 权限：非 root 用户，最小 capability，关闭特权提升。
- 文件系统：源码只读，临时目录可写。
- 网络：静态分析默认断网，动态验证使用受限内网。
- 资源：按镜像默认配置，任务结束立即回收。
- 镜像：不同技术栈使用不同扫描镜像，避免大型通用镜像。

注意：过度自定义 seccomp 可能导致 Java、Node、Python 运行失败，第一版优先使用 Docker 默认安全配置并逐步裁剪。

### 7.3 多 Agent 编排引擎

建议采用“阶段状态机 + 事件流 + 可审计任务消息”设计。

Agent 角色：

- Recon Agent：环境侦察。
- Code Audit Agent：SAST 与污点分析。
- PoC Verify Agent：动态无害验证。
- Exploit Chain Agent：攻击链推演。
- Report Agent：报告生成。

编排职责：

- 按顺序推进阶段。
- 禁止上一阶段未完成时提前进入下一阶段。
- 为每个 Agent 提供明确输入和预期输出。
- 将 Agent 输出写入持久化数据层。
- 实时发送状态、日志和进度事件。
- 处理超时、失败、停止和人工审核信号。
- 保留 Agent 执行记录，便于复盘。

### 7.4 污点追踪引擎

第一版不推荐从零实现全部 AST 和数据流算法。

推荐组合：

- Semgrep 做轻量规则扫描和基础污点检测。
- CodeQL 或 Joern 做跨文件语义分析。
- 系统统一把工具结果转换成内部漏洞对象。
- 对 Source、Sink、Sanitizer 和路径做归一化。
- 将工具结果映射到 CWE、OWASP 分类和风险模式。

### 7.5 PoC 验证与推演引擎

建议拆成两层：

1. PoC 验证层：从模板生成无害探测用例，在沙箱中执行，记录请求与响应。
2. 攻击链推演层：读取已验证漏洞和 runtimeProfile，利用漏洞能力模型生成 DAG。

第一版可先使用结构化规则库完成 SQL 注入、IDOR、文件上传等固定场景。

### 7.6 报告汇编模块

报告数据统一由 reportId 关联：

- 项目信息。
- 任务执行信息。
- runtimeProfile。
- findings。
- pocEvidence。
- fixPatch。
- attackGraph。
- 评分和风险统计。

导出现推荐：

- Markdown 作为母版。
- HTML 作为在线预览。
- PDF 作为正式交付。

## 8. LLM 接入方案

本项目默认不训练大模型，只需完成模型调用与输出规范。

推荐三种模式：

1. 在线模型模式：接入 OpenAI、DeepSeek、Qwen、通义、智谱等兼容 API。
2. 本地模型模式：通过 Ollama、vLLM 或模型下载脚本加载开源模型。
3. 演示模式：使用模板和示例数据模拟 Agent，便于没有 API Key 的用户体验完整流程。

大模型在系统中的用途：

- 汇总扫描结果。
- 分析漏洞业务影响。
- 生成修复建议。
- 辅助生成攻击链解释。
- 生成报告摘要与整改建议。

大模型不替代确定性工具：

- 漏洞位置由 SAST 和污点引擎提供。
- PoC 证据由沙箱执行结果提供。
- CVSS 使用结构化评分规则。
- 攻击链依赖能力模型和规则约束。

代码发送提醒：

- 使用在线模型时应明确告知用户源码会发送到模型服务。
- 对敏感项目应支持完全本地模型。
- 不把客户源码、密钥和未授权数据写入公开数据集。

- 沙箱已销毁。

- 新疑似漏洞已入库。

## 12. GitHub 可运行项目发布结构

建议仓库包含以下内容：

- README：功能介绍、架构说明、安装流程、模型配置、使用说明。
- LICENSE：明确开源许可。
- docker-compose：一键启动所需服务。
- .env.example：模型 API、数据库、端口等示例配置。
- backend：后端服务。
- frontend：前端工作台。
- agents：Agent 角色、提示词、任务定义。
- sandbox：沙箱镜像、启动配置和安全策略。
- scanners：扫描工具适配。
- data：示例漏洞数据。
- targets：示例靶场源码。
- docs：部署与使用文档。
- report-templates：报告模板。

不应把模型权重、客户源码、API Key、生产数据提交到 GitHub。

GitHub 发布应区分“一键演示模式”和“安全运行模式”：

- 演示模式用于展示完整页面和流程，不扫描不可信或敏感源码。
- 安全运行模式应连接独立沙箱主机、Rootless 容器、gVisor 或 Kata，不使用特权 Docker-in-Docker 作为默认方案。
- 如果为了便于本地演示而使用 DinD，应单独提供 `docker-compose.demo.yml`，并明确标注仅供演示。
- Docker 管理端口不能开放到公网，Docker API 不使用明文且无鉴权的默认配置。
- PostgreSQL、Redis、PgAdmin 等调试端口默认只绑定 `127.0.0.1` 或仅由内部网络访问。
- LLM API Key 只能从 `.env` 或安全密钥服务读取，不能写入数据库或返回给前端。
- 源码上传和源码快照需要明确保留周期，避免 GitHub 示例版本意外保存用户代码。

## 14. 可用的示例场景

## 17. 主要风险与注意事项

1. 自动化动态验证很难覆盖所有漏洞类型，第一版应优先固定演示靶场场景。
2. PoC 必须在隔离沙箱内执行，不能直接扫描未授权系统。
3. 静态工具结果需要统一规范化，不能直接把不同工具的输出混合展示。
4. LLM 生成的补丁需要语法、编译和安全回归校验，不能直接自动应用。
5. 在线模型会接触源码，仓库应提供本地模型选项和用户确认提示。
6. 沙箱配置不宜过度约束，先确保运行环境可用，再逐步加固。
7. 用户停止任务后必须持久化阶段产物，避免执行中断导致全部结果丢失。
8. 攻击链推演应基于结构化能力和规则，避免完全依赖模型自由发挥。

新增的 08-11 文档属于蓝图的具体化设计，不是替代方案。蓝图负责约束业务规则，08-11 负责约束实现细节：

| 文档 | 定位 | 对应蓝图章节 |
|---|---|---|
| 08_API接口契约 | 前后端接口契约 | 第 11 章 |
| 09_数据库表结构设计 | 数据模型与存储设计 | 第 4 章、第 6.5 节 |
| 10_WebSocket事件协议 | 实时事件与前端联动 | 第 10 章 |
| 11_Docker容器编排拓扑 | 部署、沙箱与一键启动 | 第 7.2 节、第 12 章 |

后续开发时如果出现不一致，以以下规则为准：

| 一致性事项 | 最终规则 |
|---|---|
| 项目删除 | 默认归档或软删除，不级联删除已保留证据和报告 |
| 项目与任务状态 | project.status 使用 active/archived；task.status 使用 created/running/completed/failed/stopped |
| 严重等级 | 存储和 API 使用 critical/high/medium/low；报告展示映射为极高危/高危/中危/低危或安全 |
| PoC 失败 | 存在风险模式时进入 latent；只有证据明确说明风险不成立才标记误报并保留审计记录 |
| 攻击链 | 必须支持 DAG 分叉；边表达依赖，节点层数仅用于布局 |
| 源码统计 | source_snapshot 必须包含总代码行数，供报告使用 |
| 报告接口 | 必须提供完整报告内容预览，不能只提供摘要和下载 |
| 补丁接口 | 必须支持补丁详情、复制/导出和采纳状态更新 |
| 用户角色 | MVP 可使用静态 Token；后续需要 users、roles、project_members 相关表 |
| API Key | 只放 .env 或安全密钥服务，不入数据库，不通过前端接口回显 |
| Docker 默认 | 公开仓库不得以特权 DinD 作为安全沙箱默认方案 |
| 数据保留 | PoC 证据、报告、审计日志按保留策略管理，不因项目删除全部清除 |
